## Applied student onboarding schema

The applied [student-onboarding.sql](../backend/supabase/student-onboarding.sql) adds the separate live `student_profiles` table tied to Supabase Auth. Its 14 columns, Auth foreign key, and four own-row policies have been verified. The migration leaves the two original tables intact and does not create a Storage bucket. Native profile routes use the student's JWT through the Supabase Data API. The connected frontend service also uses authorized, parameterized PostgreSQL transactions that recheck the actor and scope every profile operation to that user.

| Student API field | Shared profile representation | Requirement |
| --- | --- | --- |
| `name` | `full_name` | Required to finish |
| `academicYear` | `academic_year` | Required to finish |
| `major` | `major` | Required to finish; Undeclared is allowed |
| `interests` | String array | At least one interest to finish |
| `goals` | String array | Optional |
| `bio` | Text | Optional |
| `skills` | String array | Optional |

The shared profile includes completion metadata. PDFs and their private metadata remain in the backend's `data/resumes` filesystem directory, with student ownership enforced through the API. They use neither Supabase Storage nor SQLite in shared runtime. Keep a persistent backend volume and one instance until shared private Storage is integrated. No Storage objects or Storage access rules were inspected by this schema review.

Shared runtime validates Supabase sessions, requires a provider-confirmed `@usc.edu` email, and maps each student request to its Auth user ID. Student-only API checks operate alongside profile ownership and restrictive USC policies. An absent profile row represents onboarding not started; completion requires the explicit API action, required basics, and an uploaded private résumé PDF. The server verifies the saved file metadata independently of profile JSON or any historical completion timestamp. The additional workflow tables below have their own server-enforced application and club-permission boundaries; the profile policies alone do not establish those permissions. Shared resume object storage is still separate work.

The current student API has explicit academic-year codes. The mock table's `year` is free text, and its actual values are unknown because records were not read. Confirm any mapping without changing the existing test data.

## Applied shared frontend workflows

The approved [shared-workflows.sql](../backend/supabase/shared-workflows.sql) migration adds eight tables and is applied to the live project:

| Table | Role |
| --- | --- |
| `odysc_student_workspaces` | Own personal state, drafts, club list, calendar/reminder preferences, optional profile extras |
| `odysc_club_memberships` | Pending/invited/active officer context with administrator/reviewer access |
| `odysc_club_settings` | Authorized club metadata, questions, deadlines, contacts, and justified optional USC ID requirement |
| `odysc_applications` | Unique student/club submission with reviewed profile/answer snapshot |
| `odysc_answer_bank` | Exact submitted answers retained only with explicit consent |
| `odysc_reviews` | Reviewer scores and administrator decisions |
| `odysc_interviews` | Actual times, meeting/location details, and owner booking |
| `odysc_club_events` | Events entered by authorized club administrators |

All eight tables have RLS enabled and no direct `anon`, `authenticated`, or `PUBLIC` grants. The backend's pinned-project, verified-TLS connection performs parameterized operations; private transactions verify current confirmed USC identity and enforce ownership, active club membership, and administrator requirements. Browser role/identity fields do not authorize access. The four existing profile ownership policies and restrictive USC policy remain intact.

The initial administrator for NSBE club `36288` was explicitly authorized and linked. Other officer signups remain requests; no first-signup administrator promotion exists. A USC ID is optional, is not enrollment verification, and is excluded from application snapshots without a stated club reason plus student consent. Existing club/mock rows were not repurposed for these workflows. See [SHARED_WORKFLOWS.md](SHARED_WORKFLOWS.md).

## Connection status

The operator inspection used `sslmode=verify-full` with the user-supplied public CA. A copy is kept in the ignored backend path `data/certs/supabase-root.crt`, referenced through the backend environment variable `SUPABASE_DB_CA_FILE`. Connection credentials remain outside this document and the repository.

Supabase Auth, student profiles, the existing directory, and shared frontend workflows are connected. Browser `/api/*` routes persist applications, answer memory, personal workspace/calendar state, authorized officer edits/reviews, and interview records. Shared event routes return actual stored events and may be empty. Some older native `/api/v1/*` placeholders still return `503 FEATURE_NOT_CONNECTED`; they are not the browser implementation.

Student signup, confirmation/resend, and password-recovery APIs are implemented against Supabase Auth; they do not require another application-table migration. The frontend includes connected account/email-flow screens. [Auth integration](AUTHENTICATION.md) covers callback allowlisting, frontend destinations, email delivery, and the same-browser PKCE cookie requirement. Live USC demo sign-in, own onboarding read, draft save/readback, and sign-out passed. Actual signup/confirmation and recovery through a real inbox, SMTP delivery, and deployed redirect URLs remain untested; the demo account was manually auto-confirmed. That does not establish inbox delivery.

Live rollback-only verification passed own-profile CRUD, cross-student isolation, and denial checks for non-USC, unconfirmed, anonymous, and stale-email-token identities. The hook body was exercised as its `postgres` owner, and catalog checks confirmed `supabase_auth_admin` execute permission; the managed database does not permit `SET ROLE supabase_auth_admin`. Direct non-USC Auth rejection separately proved the configured hook is active. Run `npm run usc:status` or `npm run usc:verify` from `backend` with `psql` on `PATH` and the configured verified TLS connection.
